# External deployment scripts

Status: implemented.

## Problem

Developers need to host generated update files on their own HTTPS infrastructure and repeat the upload reliably. The package already prepares signed releases, but its JSON output does not describe the files and HTTP metadata an uploader needs. Local publication success also does not establish that a remote host serves the release.

## Design

Keep uploads in a project-owned script. The package does not configure cloud accounts, provision hosting, manage credentials, or execute lifecycle hooks.

Add a `deployment` object to the existing `publish --json` result. Its independently versioned schema contains the absolute local output directory, the HTTPS base URL, and an ordered file array. Each entry contains its relative path, URL, role, SHA-256, byte size, content type, and cache policy. The array includes only the current release's IPA, manifest and metadata, followed by the installation page and finally the feed. Existing top-level publication fields and the hosted feed protocol remain compatible.

Use the same upload and verification path for withdrawals. `withdraw --base-url … --json` describes only the page and feed, in that order, and preserves release assets. Active publications retain deployment schema version 1. Withdrawals use version 2 with `operation: "withdraw"` and `release: null`, so older consumers reject them before uploading. The hosted feed schema remains version 1.

Add `verify --publication <report.json>`. It validates the report, downloads each expected file through HTTPS, compares sizes and digests, and checks content types and cache policy. It streams large artifacts and fails on missing, stale, corrupt, or incorrectly served files. HTTPS redirects remain HTTPS. Verification does not require the local artifacts and does not prove device installation or that a CDN will obey its headers at every edge.

Provide a copyable S3 example using the normal AWS CLI and a project-owned wrapper. Read upload metadata from the report rather than inferring filenames or headers. Check all local artifacts before uploading, upload files in the given order, and run verification before printing success and installation links. Keep credentials, bucket access, HTTPS delivery, and CI serialization in the user's existing tooling.

## Operational contract

- A successful `publish` prepares the local site. Only the deployment wrapper reports remote completion, after verification.
- Keep the JSON report outside the served directory. It contains local paths and is workflow metadata, not part of the website or feed.
- Serialize the whole prepare/upload/verify workflow per app and channel, including across machines. The publisher's local file lock does not protect remote deployment.
- Preserve the prepared directory and report for retries. A failed upload can be retried without rebuilding, deleting older releases, or changing the release identity.
- Upload complete release assets before the page and feed. Feed-last prevents update clients from being offered absent assets; separate remote object writes are not a transaction.
- Keep prior release assets available. Cache immutable release assets; revalidate the page and feed. CDN configuration must honor these headers.
- The phone's installer must reach the manifest and IPA independently of app-specific credentials.

## Decisions

A shell or CI wrapper is the extension point because it already supports configuration, sequencing, exit status, and provider-specific commands. A generic post-publish hook would not enforce upload ordering and would blur local and remote failure. Phased hooks would introduce a deployment framework without removing provider-specific consistency requirements.

The ordered report is additive CLI metadata. It does not change the Swift client or require a hosting adapter. Checksums cover the exact generated bytes, so endpoint verification also detects rewritten manifests or stale feeds.
